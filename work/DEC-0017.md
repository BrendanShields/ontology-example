The candidate spec asked for a logic layer in which each rule names the Python function that implements it and the tests that cover it, and for an action layer compiled into a typed SDK. The generated action layer is rejected in DEC-0011, with its reasons, and is not argued again here. This Decision is about how a rule is tied to code without it.

| | Dotted path in the ontology | Annotation plus discovery (chosen) |
| --- | --- | --- |
| What the glossary says | `scoring.conclude` implements `score` | `score` is `binding: computed`. `RejectionRule` is `binding: rule` |
| A function is renamed or moved | an OntologyChangeRequest and a person's approval | `onto gen` rewrites the bindings manifest. `onto gen --check` fails until it is rerun |
| A declared path goes stale | possible: the declaration and the code are two statements | not possible: the binding is read from the code |
| The proof | a second list of tests in the ontology | the chain that exists: a done Requirement that uses the term, a Test that verifies it, passing Evidence |

How it works:

- `onto rules` reads each file under a context's `domain_paths` and `write_paths`. A rule is produced where `<Enum>.<VALUE>` is written inside a function, other than in a comparison or a `match` pattern. A computed slot is produced where `<slot>=` is passed by name to a generated class that carries it.
- `unbound-rule`: no function produces the term. `unproven-rule`: no done Requirement of the context lists the term and is verified by a Test with passing Evidence.
- `onto gen` writes what it found to `<context>.bindings.json`, a generated file.

Evidence:

- A prototype of the gate, run during validation on an annotated copy of the repository, found a producing function for all six rules of that day and all three computed slots. It failed on four rules with no proof: three were tested under REQ-0001 and not named by it, and one had a test and no Requirement. Those became REQ-0012 to REQ-0015.
- Run for this record on 2026-11-26, `bin/onto rules` reports 10 bound terms, 0 errors and 0 warnings.

Limits, stated so that nobody reads more into the gate than it holds:

- The code half goes by name. A term that appears in a parameter default, a return annotation or dead code counts as produced.
- The proof half checks that a verified Requirement lists the term. It does not check that the Test exercises the rule.
- A value built through `Cls(**data)`, `model_validate` or `Enum[name]` is not seen. `onto rules` warns with `hidden-binding` only when a term that could come from there is unbound.
- `precondition_of` is built and tested on a toy glossary only. The call-qa glossary declares none, because the verbs it would name are not terms yet.

This Decision would change with DEC-0011: a second kind of effect outside the process would justify a shared action shape, and the bindings would then hang from it.
