The seven stages that `onto view` reports end at ship. The question was what a framework that claims the whole lifecycle owes after that. The answer has no new stage: work that comes back from operation enters at intake again, with a link that says where it came from.

| Considered | Verdict | Reason |
| --- | --- | --- |
| `Incident`, with `breaks` and `observed_on` | adopted | without it, "which Requirements broke in operation" and "which Incidents have no verified fix" cannot be asked of the graph |
| `raised_from` on a Requirement | adopted | records that a Requirement exists because of an Incident |
| `replaces` on a Requirement | adopted | a business rule changes by a new Requirement, and "what did this rule use to say" keeps an answer |
| `affects` on a Decision | adopted | a Decision about files, not terms, was never given to the Task that touched them |
| a Release class | deferred | a Change ends at a pull request, and a git tag says what a version holds |
| an operate or observe stage | rejected | telemetry is not a file in git, and nothing here could check it without a model or a network call |
| separate Constraint and AntiPattern classes | rejected | a Decision that is done is a constraint, and a denied synonym is the anti-pattern that can be checked exactly |
| a status machine for work items | rejected | status is a field, and each gate reads one snapshot of the graph |

The change to the workflow ontology is OCR-0004. What holds it:

- `gate:ClosedIncidentIsFixed`: an Incident is done only when every Requirement it `breaks`, and every Requirement `raised_from` it, is done, and there is at least one. A done Requirement is held to a Test with passing Evidence by the gate that was already there.
- `gate:ReplacedRequirementIsMarked`: a Requirement replaced by a done one reads `superseded`, a superseded one is replaced by one that is done or itself superseded, and no chain leads back to its start.
- `onto validate`: `incident-superseded` and `replaces-cycle` are errors. `withdrawn-early`, `incident-undated` and `stale-affects` are warnings.
- CQ-08, CQ-09 and CQ-10 ask the three new questions. The Incident and Rule change playbooks are the routes.

Evidence from validation: a Release class with `includes` and `version_tag`, added to a scratch copy of the workflow ontology, worked with `onto gen`, `onto new` and `onto validate` and no change to the code. So deferring it costs little: it is an OntologyChangeRequest away.

Limits a reader must know:

- The Incident gate reads statuses. An Incident that `breaks` a Requirement which was never set back from `done` can be closed at once. The playbook says to reopen the Requirement, and nothing checks it.
- There is no worked Incident in `work/`. Nothing in this repository's history was observed in operation, and one would have been invented. The tests, the adoption test and the playbook are the example.
- A Requirement cannot be withdrawn with nothing in its place, and nothing can be removed from the record.

This Decision would change when a team needs a gate that only a Release can state, such as "a Release includes only done Changes", or when evidence from operation arrives as a file a gate can read.
