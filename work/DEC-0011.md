Considered and rejected: a generic action layer compiled from the ontology, in which every verb has a target class, preconditions, a `dry_run()` and a `stage()`.

| | Generic action layer | One ledger for the one effect (chosen) |
| --- | --- | --- |
| Verbs it would serve today | record a Finding, complete an Evaluation, publish | publish |
| What a dry run would add | nothing: `guardrails.check_finding` and `session.outstanding` already answer with Rejections and record nothing | not needed |
| What staging would add | nothing for the first two: an `EvaluationSession` holds Findings in memory until `finish` | the one place an effect happens |
| New vocabulary | action, precondition, dry run, effect: none is a glossary term | PublicationState, Review, AuditRecord, all approved in OCR-0005 |
| Cost | a compiler and generated classes nobody instantiates | two modules of about 200 lines each |

Evidence, from the validation that preceded this work (`runtime-two-gate` and `data-logic-actions` findings):

- The model has two tools and neither has an external effect. A probe showed `check_finding` on a bad proposal answering `UNKNOWN_UTTERANCE` with nothing recorded, and `record_finding` accumulating Findings with no Evaluation until `finish`: the dry run and the staging already exist under the repository's own names.
- A prototype ledger of about 80 lines refused publication before a person's Review, published after it, and refused a second publication. 2,730 sequences of events against its transition function showed no violation.
- Grep of the app found no file write, log or network call other than the model request, so publication is the first effect and the only one.

Revisit this when a second kind of effect appears. Two would justify a shared shape. One does not.

What the ledger is:

- One file, named by the caller, of JSON lines. A line is written only after the domain layer permitted the change (DEC-0010), and holds identifiers, states and times (DEC-0009).
- Reading it runs every line through the domain layer again. A line that records a change the state machine does not permit makes the read fail. That is a check of consistency and not of who wrote the file: a line that was removed is not noticed, and a staging line whose disposition was changed from NEEDS_REVIEW to FINAL reads as true and is then published without a Review. Whoever can write the file can publish.
- Publishing means recording PUBLISHED. No system receives the Evaluation, and the ledger does not keep it: whoever staged it has it on stdout.

What it is not: there is no lock, so two writers at once are not safe. A reviewer is an unauthenticated string. It is a record of what was permitted, not an access control. A team adopting this replaces the file with whatever its system of record is and keeps the domain layer.
