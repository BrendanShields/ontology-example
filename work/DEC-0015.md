"Formal verification" in this repository means this: the real code is run on every case within a stated bound, each result is checked against the Requirements, and planted faults show that each check can fail. It is every case within a bound. It is not a proof, and nothing here says "proved".

Three tools were tried on the same target during validation. The numbers in this table were measured then, on prototypes in a scratch directory.

| | Bounded run of the real code (chosen) | TLA+ with TLC | z3 |
| --- | --- | --- | --- |
| What it checks | the Python that ships | a hand-written model of the loop | a hand-written model of the scoring function |
| Cost to run | 1,456,824 Evaluations in about 6.5 s, 438 session states in 0.56 s, 30,941 loop runs in 1.1 s | 191 distinct states in 0.73 s | 71 s for the whole run |
| 20 planted faults in the Python | 19 reported at first, then all 20 once a rounding property was added | the same verdict for all 20, because it never reads the code | not applicable |
| Limit | the bound | needs a separate conformance run to stay true to the code: 12 s, 205,379 runs, and it still missed one fault | proved the properties at 2 and 3 Criteria and timed out at 4 after 60 s. The shipped Scorecard has 6 |
| New dependency | none | Java and a pinned jar on every machine that records Evidence | a 90 MB package |

The same 20 faults were also run against the example tests the app had then, five random seeds each. Sixteen were caught every time. Three were never caught. One, a pass mark compared with `>` in place of `>=`, was caught in 12 of 25 runs. That is the gap the bounded checks close.

What ships, in `apps/call-qa-agent/tests/bounded/`, with counts the tests assert as literals:

- Scoring: Scorecards of 1 to 3 Criteria, weights 1 to 3, critical or not, every combination of outcomes, pass marks 0 to 100. 623,574 Evaluations and 388 lists of Findings.
- Session: 1 to 3 Criteria and a Call of two Utterances. 438 states and 34,014 steps.
- Loop: 2 Criteria and 0 to 4 turns over 13 kinds of turn, against a scripted stand-in for the model. 30,941 runs.
- Ledger: every sequence of 0 to 5 commands over 9 commands, for one Call and one Scorecard. 66,430 sequences.
- Mutants: exact swaps of source text, each applied to a copy of the package, each of which a named property must report. A swap whose text no longer occurs exactly once fails, so a person looks again when a guarded line changes.
- Two state diagrams generated from the runs, with a test that fails when a committed diagram and the code disagree.

Outside the bound: more Criteria or heavier weights, the SDK's parsing of a response, the refusal fallback, the Bedrock client, the content of the requests sent to the model, two writers on one ledger, and a write cut short. The oracle is one author's reading of the Requirements. Mutants show that a check can fail, not that the oracle is right.

A model checker is the right tool when the question is about order between actors: concurrency, interleavings, retries, crash and resume, or whether something always finishes. Listing inputs to one thread cannot show an interleaving. The nearest case in this repository is two commands on one ledger at once, which today is held by a file lock and example tests. A model then needs its own conformance check against the code. The `bounded-verification` skill says the same.
