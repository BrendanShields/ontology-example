# Adopting the ontology gates in another repository

This guide is for an engineer who wants the gates of this repository in a
repository of their own. It takes you from an empty ontology layer to one
Requirement verified by a test, with CI and code owners wired.

The tool is `onto`, the Python package under [`packages/onto`](../packages/onto).
`onto init` writes everything else into your repository.

## What you need

- A git repository. `onto init` refuses to run outside one.
- Python 3.11 or later.
- pytest, if you want the traceability gate. Evidence is recorded from pytest runs only.
- `make`, if you want the `onto-*` targets. Nothing depends on them.
- Claude Code, if you want the hooks, skills and agents. Without it, pass `--no-claude`.

The examples use [uv](https://docs.astral.sh/uv/). Any installer works: see
[The onto command](#the-onto-command).

## Install onto

`onto-cli` is not published to a package index. Install it from this repository.

Build a wheel and add it to your development dependencies with the `gen` extra:

```bash
# in a checkout of this repository
uv build --package onto-cli --out-dir dist

# in your repository
uv add --dev "onto-cli[gen] @ file:///path/to/dist/onto_cli-0.1.0-py3-none-any.whl"
```

Or depend on the git repository directly:

```bash
uv add --dev "onto-cli[gen] @ git+<URL of this repository>#subdirectory=packages/onto"
```

The wheel route was run by hand, in a new uv project and in a clean virtual
environment. The git route was not. The test suite of this repository runs
`onto init` from its own editable install. The `gen` extra brings the LinkML
generators that `onto gen` needs. The gates themselves run without it.

Check the install:

```bash
uv run onto --version
```

## Scaffold the ontology layer

Run `onto init` anywhere inside your repository. It works at the top level of
the git repository.

```bash
uv run onto init \
  --context loans \
  --domain-path "src/loans/domain/**" \
  --base-uri https://ontology.your-org.example
```

| Option | Meaning | Default |
| --- | --- | --- |
| `--context NAME` | The bounded context to start a glossary for. Lower case, digits, `-` or `_`. Not `linkml`. | `app` |
| `--domain-path GLOB` | The domain layer of that context, as a glob from the repository root. Vocabulary is enforced there. The generated types go in the folder above it. A folder without a glob gets `/**` added, and a leading `./` is dropped. | `src/<context>/domain/**` |
| `--base-uri URI` | The namespace of your ontologies and work items. An http or https URI without spaces, quotes or angle brackets. | `https://example.org` |
| `--onto-cmd COMMAND` | How hooks, make and CI run onto. | `uv run onto` |
| `--no-claude` | Leave out the Claude Code layer. | off |
| `--no-ci` | Leave out the CI workflow. | off |

Choose the base URI once. It is written into the workflow ontology, the gates,
the competency questions and the glossary. It does not have to resolve.

### What it writes

| Path | What it is |
| --- | --- |
| `onto.toml` | Where the ontology layer lives and which code each context governs. Every command reads it. |
| `ontology/workflow.yaml` | The workflow ontology: Requirement, Task, Decision, Test, Change, Evidence, OntologyChangeRequest. |
| `ontology/shapes/gates.shacl.ttl` | The hand-written graph gates. |
| `ontology/cq/*.rq` | The competency questions. |
| `ontology/domains/<context>.yaml` | A starter glossary with three placeholder terms: `Item` (alias `entry`), `Owner` (denied synonym `Holder`) and `Label`. |
| `ontology/schemas/`, `ontology/shapes/workflow.shacl.ttl`, the context's `generated.py` and `schemas/` | Generated by `onto gen`, which `onto init` runs last. Commit them. |
| `work/README.md` | The guide to the work items. |
| `.gitignore` | Gains `work/evidence/` and `prov/*.ttl`. |
| `onto.mk`, `Makefile` | The targets `onto-gen`, `onto-check` and `onto-view`. A Makefile gains one line, `include onto.mk`. |
| `.github/workflows/ontology-gates.yml` | The CI workflow. |
| `.claude/settings.json` | The hooks and one permission. |
| `.claude/skills/`, `.claude/agents/` | The workflow skills, their playbooks and the four agents. |
| `.claude/pstack/`, `tools/check_vendored.py` | The MIT licence, the notice and the pinned upstream files of the skills adapted from pstack, and the script that checks them. |
| `CLAUDE.md` | A short section that points an agent at the workflow. |

### What it does to files you already have

`onto init` never overwrites a file. It prints one line per file:

| Status | Meaning |
| --- | --- |
| `written` | The file was not there and is now. |
| `exists` | The file was there and was left as it is. |
| `merged` | Lines or entries were added. Nothing that was there was changed or removed. |
| `unchanged` | The file already had what `onto init` would add. |
| `beside` | The file could not be added to safely. The content was written to a file beside it, and the line says what to copy. |
| `skipped` | Nothing was written, and the line says why. |

- `.gitignore`: missing lines are appended.
- `Makefile`: `include onto.mk` is appended. The targets start with `onto-`, so they do not replace yours.
- `.claude/settings.json`: the permission rules and the hook groups are added to yours. If the packaged settings deny editing generated files, that rule is written once for each generated file your `onto.toml` names, and for `work/evidence/**`. If the file is not plain JSON, or a list under `permissions` or `hooks` has an unexpected shape, yours is left alone and `.claude/settings.onto.json` is written beside it. If that file exists too, it is left alone and reported as `exists`.
- `CLAUDE.md`: if you have one, the section is written to `CLAUDE.onto.md`, unless that file exists too. Copy it in and delete that file.
- A file where `onto gen` would write, such as an existing `src/loans/generated.py`: `onto init` stops before generating and names the file. Point `pydantic`, `json_schema` or `glossary_json` somewhere else in `onto.toml`, then run `onto gen`.

Running `onto init` again with the same options is safe. It writes what is
missing and changes nothing else. It does not update a file it wrote earlier:
see [Limits](#limits). With a different `--onto-cmd` it adds a second set of
hooks to `.claude/settings.json`, because a hook is recognised by its exact
command. Change the command by hand instead: see [The onto command](#the-onto-command).

### Check the result

```bash
uv run onto gen --check     # generated files match the ontology
uv run onto validate        # work items and the glossary are valid
uv run onto check-terms     # the domain layer uses glossary vocabulary
uv run onto trace           # traceability and graph gates
uv run onto overview        # the glossary as an agent reads it
```

All five exit 0 on a fresh scaffold. Commit everything `onto init` wrote.

## The onto command

Hooks, the make targets and CI all run onto through one command string, set
with `--onto-cmd`. The command must work from any folder inside the repository
and without an activated environment.

| File | Where the command is |
| --- | --- |
| `.claude/settings.json` | In each hook, after `cd "$CLAUDE_PROJECT_DIR" &&`, and in `permissions.allow`. |
| `.claude/skills/`, `.claude/agents/`, `CLAUDE.md`, `work/README.md` | In the instructions an agent follows. |
| `onto.mk` | The `ONTO` variable. Override it with `make onto-check ONTO=...`. |
| `.github/workflows/ontology-gates.yml` | The `ONTO` variable under `env`. |

To change the command later, edit those places. `onto init` does not rewrite them.

The CI workflow runs `$ONTO <subcommand>`, and the shell does not read quotes
inside a variable. A command that needs quoting, such as a path with a space,
works in the hooks and in make and fails in CI. Use a command without quotes,
or write it into each `run:` line of the workflow.

## Add your first glossary term

The three starter terms are placeholders. The glossary is a protected file: it
changes only while an OntologyChangeRequest is in progress, and a person
approves that request.

1. Check the name is free. Exit code 1 means it is not a term.

   ```bash
   uv run onto resolve Loan
   ```

2. Raise the request.

   ```bash
   uv run onto ocr new --context loans --term Loan \
     --justification "Requirements about lending need a name for it." \
     --definition "The lending of one Item to one Owner until a due date."
   ```

3. The person who owns the context's language reads `work/OCR-0001.md` and sets
   its `status` to `in_progress`. Until then the guard hook blocks every edit
   to the glossary. After that it asks for confirmation on each edit.

4. Edit `ontology/domains/loans.yaml`. A term is a class, a slot, an enum or a
   permissible value. Give it a `description`. List names nobody should use for
   it under `annotations.denied_synonyms`.

   ```yaml
   classes:
     Loan:
       description: >-
         The lending of one Item to one Owner until a due date.
       annotations:
         denied_synonyms: [Checkout]
   ```

5. Regenerate and check.

   ```bash
   uv run onto gen
   uv run onto validate
   uv run onto check-terms
   ```

6. Set the request to `done` and open the pull request.

In Claude Code, `/ontology-change` walks an agent through the same steps and
stops at step 3.

To retire a starter term, remove it under a request in the same way. If its
name must not come back, add it to the `denied_synonyms` of the term that
replaces it.

## Take a Requirement from written to verified

1. Write the Requirement. `ears_text` is one EARS sentence with each glossary
   term in backticks, and `uses_terms` lists the same terms.

   ```bash
   uv run onto new Requirement \
     "title=Every item has an owner" \
     bounded_context=loans \
     'ears_text=The system shall record one `Owner` for each `Item`.' \
     uses_terms=Owner,Item \
     status=ready
   ```

   It prints `work/REQ-0001.md`. A name that is not a term, or a denied
   synonym, is refused and nothing is written.

2. Write the Task that implements it.

   ```bash
   uv run onto new Task "title=Record the owner" bounded_context=loans \
     implements=REQ-0001 status=in_progress
   ```

3. Write the code and a pytest test for it. Code under the domain path may use
   glossary names only: `onto check-terms` fails on a denied synonym.

4. Register the test as a Test item. `path` is a pytest node id relative to the
   repository root. The file must exist.

   ```bash
   uv run onto new Test "title=An item has its owner" bounded_context=loans \
     verifies=REQ-0001 path=tests/test_owner.py::test_an_item_has_its_owner status=done
   ```

5. Record the evidence. Either command writes `work/evidence/EVD-0001.md`.

   ```bash
   uv run onto evidence collect          # runs the pytest nodes of the Test items
   uv run pytest --onto-evidence         # or your whole suite
   ```

6. Set `status: done` in `work/REQ-0001.md` and `work/TASK-0001.md`, then run the gate.

   ```bash
   uv run onto trace
   ```

   The row for `REQ-0001` reads `verified` and the command exits 0. If you set
   `done` before the evidence exists, or the test fails, `onto trace` exits 1
   and names the Requirement.

`uv run onto view` shows the stage each Task has reached.

## After ship: incidents and rule changes

The workflow does not end at ship. Two things bring work back in, and each has
a playbook under `.claude/skills/ostack-mode/playbooks/`.

**Something went wrong in operation.** Record it as an Incident, then tie it to
a Requirement: one it shows broken (`breaks` on the Incident), or a new one
raised from it.

```bash
uv run onto new Incident "title=An item was shown with no owner" \
  bounded_context=loans observed_on=2026-03-02 status=in_progress
uv run onto new Requirement "title=Every item has an owner" bounded_context=loans \
  'ears_text=The system shall record one `Owner` for each `Item`.' \
  uses_terms=Owner,Item status=in_progress raised_from=INC-0001
```

`uv run onto view` lists the Incident with the Requirements it waits on, and
`uv run onto cq CQ-08` lists every Incident that names no Requirement or names
one that is not yet done. Take the Requirement to verified as above, then set
`status: done` in `work/INC-0001.md`. If you set it before the Requirement is
done, or name no Requirement at all, `onto trace` exits 1 with
`gate:ClosedIncidentIsFixed`. Only `done` closes an Incident: `onto validate`
refuses `superseded` on one. When an Incident `breaks` a Requirement that is
already done, set that Requirement back to `in_progress` first. The gate reads
its status, so it cannot tell that the Requirement was verified again.

**A business rule changes.** Do not edit a Requirement that is done. Write the
new rule as a Requirement that `replaces` it, restate the tests so that they
verify the new one, and set the old one to `superseded`.

```bash
uv run onto new Requirement "title=Every item has an owner or a label" bounded_context=loans \
  'ears_text=The system shall record one `Owner` or one `Label` for each `Item`.' \
  uses_terms=Owner,Label,Item status=in_progress replaces=REQ-0001
```

Once the new Requirement is done, `onto trace` exits 1 with
`gate:ReplacedRequirementIsMarked` until the old one reads `superseded`, and a
Requirement that reads `superseded` must have one that replaces it.
`uv run onto cq CQ-09 --bind requirement=REQ-0001` shows what replaced a
Requirement, all the way forward. `onto validate` refuses a Requirement whose
`replaces` leads back to itself, and warns about one set to `superseded`
before the Requirement that replaces it is done. Set the Task that delivered
only the old Requirement to `superseded` as well, and the Change that resolved
that Task: a Task that still reads `done` keeps its Requirement a claim that
needs a Test.

A Decision can name the files it constrains, as globs from the repository
root: `affects=src/loans/domain/*.py`. `onto slice --task` gives that Decision
to any Task when the branch changed a matching file, and `--file` names a file
or a folder yourself, from the directory you are in.
`uv run onto cq CQ-10 --bind path=src/loans/domain/owner.py` lists the
Decisions in force on a path. `onto validate` warns about a glob that no
longer matches any file.

## Wire CI

`.github/workflows/ontology-gates.yml` runs the gates on every pull request and
on pushes to `main`. Before you rely on it:

- Change its `Install` step to however your repository installs its
  development dependencies. `onto-cli[gen]` has to be among them.
- If your default branch is not `main`, change `branches` in the workflow and
  `base_ref` in `onto.toml`.
- Make the `gates` job a required status check on the default branch. Until
  then a failing gate does not block a merge.

On another CI system, run `make onto-check` or the commands in `onto.mk`.
Do not pass `--gate stop` there: that mode reads a hook event from standard
input and waits for it.

## Wire CODEOWNERS

The guard hook is a reminder. The control on the ontology is the review that
CODEOWNERS requires. `onto init` does not write this file, because only you
know the owners. Add lines like these and require code-owner review on the
default branch:

```text
# The workflow ontology and the gates are shared by every context.
/ontology/workflow.yaml          @your-org/platform
/ontology/shapes/                @your-org/platform
/onto.toml                       @your-org/platform
/.claude/                        @your-org/platform

# Each glossary belongs to the people who own its language.
/ontology/domains/loans.yaml     @your-org/loans-leads
/ontology/cq/                    @your-org/loans-leads @your-org/platform
```

## What is checked where

| Check | Command | Claude Code hook | `make onto-check` and CI |
| --- | --- | --- | --- |
| Generated files and evidence are not edited by hand. Ontology sources change only under a request in progress. | `onto guard` | before each Edit or Write | no |
| An edited work item is valid. An edited domain file uses no denied synonym. | `onto check-terms --changed-from-stdin` | after each Edit or Write | no |
| Every work item and glossary is valid. | `onto validate` | no | yes |
| Every domain layer uses glossary vocabulary. A context that has code and whose `domain_paths` match no file gets a warning. | `onto check-terms` | no | yes |
| Generated files match the ontology. | `onto gen --check` | no | yes |
| A Requirement claimed done has a Test with passing evidence, and the other graph gates hold. | `onto trace` | when the agent stops, for what the branch touched | yes, for everything |
| A done Requirement that replaces another leaves the old one superseded, and a superseded Requirement has one that replaces it. A done Incident names a Requirement, and each Requirement it breaks or that was raised from it is done. | `onto trace` | when the agent stops, also when the branch touched only the other end of the link | yes |
| An Incident is not `superseded`, and no Requirement's `replaces` leads back to itself. A warning for an Incident with no `observed_on`, and for a Requirement set to `superseded` before the one that replaces it is done. | `onto validate` | after an Edit or Write of the work item | yes |
| An `affects` glob of a Decision that is not superseded matches a file. Otherwise a warning. | `onto validate` | after an Edit or Write of the Decision | yes, as a warning |
| Each gate file and each question declares the namespace of the workflow ontology, and no other namespace in its place. | `onto trace` | when the agent stops, also on a branch that touched no work item | yes |
| An ontology source the branch changed has an OntologyChangeRequest on the same branch, in progress or done, whatever tool changed it. The branch that brings the ontology layer in needs none. | `onto trace` | when the agent stops | yes |
| The branch has a base to be compared with. Without one, every item is checked and the command fails until `base_ref` names a branch that is fetched. | `onto trace` | no: the uncommitted changes are judged | yes |
| Each term the glossary binds as a rule or a computed slot has a function that produces it and a verified Requirement that uses it. | `onto rules` | no | yes |
| Questions that expect no rows return none. | `onto cq --check` | no | not in the scaffolded workflow: add it if you want it |

The hooks run only in Claude Code sessions, and a person can edit any file
outside one. CI and the CODEOWNERS review are the controls.

## Limits

- **Evidence comes from pytest only.** A Test item's `path` is a pytest node id.
  A team with another test runner gets the vocabulary checks and no
  traceability gate.
- **pytest must run from the repository root.** `pytest --onto-evidence` looks
  for `onto.toml` in pytest's root directory.
- **Generated types are Python only.** `onto gen` writes Pydantic types and JSON
  Schema. Denied synonyms are found in any text file under a domain path. A
  class coined under a name the glossary does not have is found in Python
  files only, and is a warning.
- **`onto init` scaffolds one bounded context.** Add another by hand: a
  `[contexts.<name>]` table in `onto.toml` and a glossary under
  `ontology/domains/`. If `.claude/settings.json` denies edits to generated
  files, add the rules for the new context's files by hand too.
- **There is no upgrade command.** `onto init` writes missing files and never
  updates one. To take a newer workflow ontology, gate or skill, compare your
  copy with the templates of the newer onto and carry the changes across.
- **The namespace is written into four kinds of file.** If you change it after
  `onto init`, change it in `ontology/workflow.yaml`, the gates, every
  competency question and the glossary, then run `onto gen`. `onto trace`
  fails while a gate or question disagrees with the workflow ontology.
- **Some rules are checked late.** `onto new` accepts a Requirement that uses a
  term classified PII at a low risk tier. `onto trace` rejects it.
- **A replaced Requirement takes its Task with it.** The traceability gate
  reads "every Task of this Requirement is done" as a claim, also on a
  Requirement that is superseded. So the Task that delivered only the old rule,
  and its Change, are set to `superseded` too. A Task that also implements a
  Requirement still in force, or a Change that also resolves a Task still in
  force, has no route yet.
- **A Requirement cannot be withdrawn with nothing in its place.** A
  Requirement that reads `superseded` needs one that replaces it. The gate
  accepts a successor of any status, so a draft is enough for it:
  `onto validate` warns until the successor is done, and does not fail.
- **The Incident gate reads statuses, not what happened.** An Incident that
  `breaks` a Requirement which was never set back from `done` passes
  `gate:ClosedIncidentIsFixed` at once. The Incident playbook asks for the
  Requirement to be reopened, and nothing checks that it was.
- **A replaced Requirement is marked only by a done successor.** One replaced
  through a chain that ends in a done Requirement can still read `done`.
  `onto slice` leaves it out of the established Requirements. `onto view`
  shows the status it has.
- **Nothing is retired from the record.** `onto validate` holds every work
  item to the glossary and to `onto.toml`, so a term that a work item lists, or
  a bounded context that has work items, cannot be removed yet.
- **The Claude Code layer is untested in a live session.** The hook commands
  are tested by feeding them the event JSON. Nobody has watched a playbook run
  in an adopting repository.
- **The mods are not scaffolded.** The three Claude mods under `mods/` stay in
  this repository.
- **The gates comment names a test file of this repository.**
  `ontology/shapes/gates.shacl.ttl` says to add a case to
  `packages/onto/tests/test_gates.py`. In your repository, write that test
  with `onto.testing.scratch_repo`, which copies your ontology layer into a
  temporary folder.
