This approach goes wrong in predictable ways, and I'll go through four of them.

The first is taxonomy committees. Modeling everything up front repeats the 1980s. A team can spend a quarter debating class names and ship nothing.

[next]

The second is thin capture. A graph nobody feeds doesn't help. In the first 21 days of MOOSEDev's live trial there were 71 unprompted assists and 38 misses. Of the 38 misses, 35 were in the one project bootstrapped from a thinner commit history. The graph only knew what went into it.

[next]

The third is auto-merged truth. If agents merge their own ontology edits without review, one wrong fact spreads to every agent that reads it. A person has to approve changes to the ontology.

[next]

The fourth is using the wrong tool for search. Keep grep, the LSP and vector search for exploratory lookup.

[next]

Here is how I would start. Following Collate's advice, don't start from zero. In week 1, project the metadata you already have — pyproject.toml, existing schemas and Git history — and hand-author just 10 to 20 classes in one domain that causes you pain. Lock generated files with a PreToolUse hook.

In month 1, add the five-tool ontology MCP server. Compile LinkML to Pydantic and docs. Add Hypothesis tests and a PR_EVIDENCE.md file for each change.

In quarter 1, model actions with explicit reversible and irreversible tags, add decision-model routing and risk checks, and run read-only SHACL gap audits to find where the data falls short of the shapes. If week 1 doesn't catch anything, you have spent a week and you can stop there.
