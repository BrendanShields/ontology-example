This slide answers those two pushbacks. The first is to put the domain in CLAUDE.md. The second is to use vector RAG.

Start with the first. The EvoOntology paper, arXiv 2609.15779, tested six model backbones on DDR-Bench. Pasting the semantic layer into the prompt lowered five of the six on the overall score. On Claude Sonnet 5, trajectory-wise accuracy dropped by 15.0 points. My reading is that a static dump fills the context with things the current task doesn't need.

[next]

Exposing the same ontology through tools that the agent calls on demand worked better. GPT-5.5, GPT-5.6-sol and Claude Opus 4.8 reached 90.9 to 93.5% trajectory-wise, and Sonnet 5 reached 81.3%. That row is the full system, the tools plus the ontology it evolved.

[next]

Now the second pushback. MOOSEDev, arXiv 2608.13662, is titled Ontology-Grounded Project Memory for Coding Agents. It compared a typed graph with rules against the mem0 vector store on structural memory questions, such as which architecture decision record replaced an older one. On set completeness, negation and supersession, the graph scored 1.00, 0.98 and 0.98. The vector store scored 0.18, 0.06 and 0.27. Similarity search has trouble here because the old record and the new one look alike.

[next]

The boundary matters as much as the two results. GraphRAG-Bench, arXiv 2506.05690, found basic RAG comparable to or better than graph RAG on simple fact retrieval. RAG with reranking reached 83.2% evidence recall on that task. If the question is where a function is defined or which document mentions a term, grep, an LSP or vector search is the right tool. A graph is worth its cost on structural questions, such as completeness, negation and what replaced what.

So the ontology sits behind tools, and the model asks for what it needs. If the word ontology still sounds like a philosophy seminar, you already rely on several of them every day.
