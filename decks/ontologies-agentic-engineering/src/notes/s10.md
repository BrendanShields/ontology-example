Most schemas stop at nouns, and this slide argues they shouldn't. The first box is data. It holds the nouns, Customer and RefundRequest. A passive schema covers this box and nothing else.

[next]

The second box is logic, the rules. evaluate_refund() is deterministic Python. The language model never does the arithmetic. It can choose which function to call, and the function computes the limit.

[next]

The third box is actions. These are verbs, not CRUD. issue_refund is an action with preconditions, and it carries a tag that says REVERSIBLE or IRREVERSIBLE. That tag is my own convention for this talk. It is not a Palantir term.

[next]

The idea of binding data, logic and actions together comes from Palantir's Ontology, and they deserve the credit for it. Their own page says the Ontology encodes "the data, logic, action, and security of the enterprise". Their docs call objects, properties and links the semantic elements, and actions, functions and dynamic security the kinetic elements. Their Ontology SDK, OSDK, generates typed TypeScript, Python and Java clients from it.

On the slide, all three boxes feed through the orange dot into one compiled typed SDK. Here is what I take from that design for our own code.

APIs, background workers and AI agents all call the same typed functions. An agent can't take a path that a normal service couldn't, because there is only one path.

Each action declares whether it can be undone. That tells you where a human approval belongs before anyone argues about it.

Every write goes through a named action, so the audit record already exists. You don't bolt an audit log on afterwards, because the list of actions taken is the log.
