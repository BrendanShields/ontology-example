Inference is what separates an ontology from a database schema or a wiki. This slide shows the smallest example I know. Sam has a solid arrow to Tom, labelled father of. Solid lines on this slide are asserted facts, things someone stored.

[next]

A second solid arrow says Tom is the father of Leo. That is the second stored fact, and there are only two.

[next]

The dashed arc from Sam over to Leo says grandfather of. Nobody stored it. A reasoner derives it from the two stored facts every time it runs. Dashed lines are inferred. In a database you would write a join or a view for this, and every consumer would need to know the view exists. In an ontology the rule sits once, next to the types, and every query sees the derived fact.

Below the line are the engineering versions, and these are the ones I care about.

The first is transitive supersession. ADR_005 supersedes ADR_004, which supersedes ADR_001. Declare supersedes as transitive, and the old rule in ADR_001 retires without anyone editing it. An agent that asks for active decisions never sees it.

The second is disjoint classes. A Customer can never also be a SupportRep. If a payout record ends up treating a customer as a support rep, the reasoner reports a contradiction. That catches a misrouted payout before money moves.

The third is a functional property. An order has at most one refund. A second refund on the same order breaks the shape of the data, so the double refund gets caught structurally. No reviewer has to spot it in a diff.

Rules like these need a notation, and there are four standards for it.
